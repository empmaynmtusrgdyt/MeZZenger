## Build & run

Qt 6.2+, C++17, CMake 3.16+. No linter is configured. Tests: see below.

```bash
mkdir build && cd build
cmake .. -DCMAKE_BUILD_TYPE=Release   # may need -DCMAKE_PREFIX_PATH=<Qt6 dir>
cmake --build . -j
./mezzenger_server [--port 5555]      # default port 5555
./mezzenger_client
```

Tests (QtTest + Python `unittest`, stdlib only; written for the maintainer's Mac): `cd build && cmake .. && cmake --build . -j && ctest --output-on-failure` (~2 min). Unit tests live in `tests/unit`; `tests/integration/*.py` start a real `mezzenger_server` with a temp DB and a cert from `scripts/gen-cert.sh` (helpers in `support.py`; use `sync()` as a barrier instead of fixed sleeps); `tests/gui/client_harness.cpp` drives the real `LoginWindow`/`MainWindow` offscreen (`QT_QPA_PLATFORM=offscreen`, set by CTest). `MEZZENGER_SKIP_SLOW=1` skips the ~31 s login-timeout test. Disable with `-DMEZZENGER_BUILD_TESTS=OFF`.

Two executables from one CMake project: `mezzenger_server` (Core/Network/Sql, no GUI) and `mezzenger_client` (Widgets). There is no shared library; `common/Protocol.h` is header-only and included by both via the `common` include dir. README and UI strings are in Russian.

## Architecture

**Wire protocol** (`common/Protocol.h`): length-prefixed JSON over TLS (TCP + TLS 1.2+) — 4-byte big-endian length header + compact JSON. `MaxMessageSize` is 1 MiB. Message kind is the string in the `"type"` field (`login`, `register`, `auth_response`, `user_list`, `message`, `message_history`, `get_offline_messages`, `search_user`, `search_user_response`, `mark_messages_read`, `message_ack`, `delivery_ack`, `presence`, `change_password`, `change_password_response`, `file_upload_request`, `file_download_request`, `file_ticket`, `file_put`, `file_get`, `file_info`, `file_result`, `error`). `user_list` contains every other user with an `online` flag; the server broadcasts `presence` (`id`, `nick`, `online`) to the other logged-in clients on login, logout and new registration (also how clients learn about new users). `search_user` is still served but the client no longer uses it: its search box filters the sidebar locally. `login`/`register` carry `protocol` (`Protocol::Version`) and the server rejects any other version with a message telling which side to update; bump `Protocol::Version` on every incompatible protocol change (adding optional fields does not need a bump). Adding a message type means updating three places: the `MessageType` enum, the `ProtocolHelper::create*` builder, and `parseMessageType` (unknown types silently map to `MessageType::Error`), plus handlers on server/client. The client side of the protocol (framing, TLS, login, reconnect) lives in `client/ServerConnection`; `ClientHandler` does the same on the server.

**Server**: `ServerCore` owns a `QSslServer` (needs `server.crt`/`server.key`, see `scripts/gen-cert.sh`; plaintext clients are refused at handshake), a `DatabaseServer` (SQLite, `server.db` in the CWD), and a `QMap<userId, ClientHandler*>` of online users. Each connection gets a `ClientHandler` that does auth (login/register), persists messages through `DatabaseServer`, and emits `messageReady` so `ServerCore::sendMessageToUser` routes to the recipient if online; otherwise messages stay undelivered in the DB and are sent via `deliverOfflineMessages` on next login. Single-threaded, event-loop driven. `ClientHandler::sendMessage` deliberately does not require authentication: failed login/register responses are sent before the client is authenticated (a check there silently swallowed them once). Registration requires a one-time invite (`invite` field in `register`; hash stored in the `invites` table, created with `mezzenger_server --new-invite`, which works while the server runs); the invite is checked before the nick so taken nicks can't be probed, and consumed in the same transaction as user creation.


**Files**: sent over a separate TLS connection to the same port so the chat channel is never blocked. Flow: the logged-in client asks on the main channel (`file_upload_request` with name/size/`ref`, or `file_download_request` with `file_id`), the server answers `file_ticket` with a one-time `token` (valid 5 min, max 10 open per user; `FileStore`). The client opens a second connection and sends `file_put`/`file_get` with the token as its first frame (no login needed, the token is the identity; `ClientHandler::startFileSession` hands the socket to `FileSession`). Upload: after the header frame come exactly `size` raw bytes, then the server replies `file_result`. Download: server sends `file_info` then the raw bytes and closes. A finished upload is attached to a normal `message` via `file_id` (text may then be empty); the server takes name/size from its own `files` row, never from the message, and only lets the owner attach a complete file. Download is allowed for sender and recipient of a message carrying the file. Files live in `files/<id>` next to `server.db`; `FileStore::initialize` deletes `*.part`, uploads unfinished for >1 h and unattached files older than 1 day at startup. Limits: 50 MiB per file, 2 GiB per user (`ServerLimits.h`, `Protocol.h`); log redacts tokens. Client side: `FileTransfer` (one transfer), `MainWindow::attachFile/downloadFile`; the file message goes through the normal pending/ack machinery only after the upload succeeded.

**Passwords and limits**: `change_password` needs the old password, counts wrong old passwords as failures per IP like login does, and replies with `change_password_response` (not `auth_response`). passwords are stored as `pbkdf2-sha256$600000$<salt>$<hash>` (Qt `QPasswordDigestor`, no extra dependency); old unsalted SHA-256 hashes are still accepted and upgraded on the next successful login. `server/ServerLimits.h` (not `Limits.h`: that name collides with the system `<limits.h>` on case-insensitive filesystems when `server/` is on the include path) holds the server-side limits (5 failed logins/registrations/invites per 10 min per IP -> blocked, checked before hashing; 30 s to log in; 4 KiB frame cap before login; 20 connections per IP / 200 total; token bucket of 60 + 20/s per connection) and `server/RateLimiter.h` the helpers (`ipKey` folds IPv6 to /64, v4-mapped to IPv4). Limits on user data (nick 2-32, password 4-128, message 4000 chars) live in `Protocol.h` and are enforced both in the client UI and on the server. Rate-limit state is in memory: restarting the server clears lockouts. The server log redacts `password` and `invite`. Changing a limit that the client also knows about does not need a protocol bump unless honest clients would start failing.

**Delivery guarantees**: a message becomes `delivered` on the server only after the recipient sends `delivery_ack` (writing to the socket is not enough). Unacked messages are offered again via `get_offline_messages` (batches of 100, ordered by id). The sender attaches a `client_msg_id` (UUID); the server stores it with a unique index per sender, answers with `message_ack` (also for retries) and does not forward duplicates. The client stores outgoing messages locally with `status = 0` until `message_ack`, and resends them after each login (when `user_list` arrives); incoming messages are deduplicated by `(my_nick, server_id)`. Old clients that don't send acks would get every message redelivered at each login.

**Client**: `main.cpp` shows `LoginWindow` (host/port/nick/password/invite), which opens one `ServerConnection` and tries to log in/register. On success the same connection (already authenticated, no second connect) is handed to `MainWindow` via `loginSuccessful(ServerConnection*)`; `MainWindow` reparents it, enables auto-reconnect (3 s timer, re-login on every reconnect) and calls `startDispatch()`. Until then `ServerConnection` holds back every message except `auth_response`, so a `user_list` sent right after login is not lost. `MainWindow` keeps all known users in `m_users` (sidebar: online first, then alphabetical; Enter in the search box opens the first match), shows unread count in the window title and alerts/tray notifications for new messages, and has an "Аккаунт" menu with password change. It owns a `DatabaseClient` and only talks to the server through `ServerConnection::send` / `messageReceived`. Chat history is cached locally in SQLite (`mezzenger_client.db`, CWD) keyed by `user_id` + `my_nick`; unread state is tracked both locally and reported to the server via `mark_messages_read`. `DatabaseClient::initialize` migrates a legacy `messenger_client.db` to the new name on first start. Styling comes from `client/styles.qss` (dark theme), listed in the client sources in CMake. Server certificates are self-signed and trusted by pinned SHA-256 fingerprint (`client/TlsTrust`, stored in `QSettings` under `trusted/<host>:<port>`; confirmed by the user on first connect). `QSslSocket::ignoreSslErrors` is sticky per socket, so `TlsTrust` resets it on every connection attempt — keep that or reconnects skip the fingerprint check.
